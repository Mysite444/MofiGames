# Making MofiGames survive a Supabase outage

## The problem

Before this change, a Supabase outage took the entire site down — not just
game data, pages with zero database dependency failed too. Two things
caused that:

1. **`src/middleware.ts`** ran `await supabase.auth.getUser()` with no
   try/catch, on nearly every request (the middleware matcher covers all
   routes except static assets). If Supabase's auth endpoint couldn't be
   reached, this threw, middleware crashed, and Next.js returned a 500 for
   every route on the site.
2. **No durable fallback data.** The app already had an in-memory TTL
   cache (`fragment-cache.ts`, `metadata-cache.ts`), but it's scoped to a
   single running server instance and wiped on every cold start / redeploy.
   The data-fetching functions behind games, categories, the homepage
   layout, and About/Contact/custom pages had no try/catch at all — a
   Supabase error just propagated up and crashed the page. On a fresh
   serverless instance spun up *during* an outage, there was nothing warm
   to fall back to.

Neither of these is really about "using Next.js static generation" in the
literal sense — the app's Supabase client is cookie-bound (for
RLS + admin-preview support), which forces most pages to render
per-request rather than being pre-rendered as static HTML. Chasing true
ISR would mean decoupling every public read from that cookie-bound client,
which is a much larger, riskier rewrite. What actually delivers "the site
stays up when Supabase doesn't" is the two fixes below.

## What changed

### 1. The middleware no longer takes the whole site down

`supabase.auth.getUser()` is now wrapped in try/catch with a 4-second
timeout. If it fails, the request is treated as signed-out and continues
normally — an outage degrades to "ask this visitor to sign in again next
time they need auth," not a 500 for every visitor.

### 2. Every public data function has a real, durable fallback

A build-time snapshot of the public-facing data lives at
`src/data/fallback/*.json` — games, categories, site identity, SEO
settings, and pages (About/Contact/custom nav pages). It's generated by
`scripts/generate-static-fallback.ts`, wired into `npm run build`
(runs automatically, no CI changes needed), and committed to the repo like
any other source file — so it ships with every deploy, survives cold
starts, and is what's on disk from the very first request even before any
live Supabase call has ever succeeded.

Every function in `games-server.ts`, `content-server.ts`,
`homepage-layout-server.ts`, `site-identity.ts`, and `seo-settings.ts` that
backs a public page now follows the same pattern:

```
try live Supabase read (bounded by an 8s timeout)
  → on failure, log it and answer from src/data/fallback/*.json
  → (site identity / SEO settings fall back once more, to a hardcoded
     default, only if even the snapshot file is missing)
```

This covers everything on your list: game names, slugs, thumbnails,
categories, descriptions, SEO meta, homepage featured games, nav, footer,
About Us, Contact Us.

Two smaller, related fixes:

- **Client-side nav/games hook** (`real-games-client.ts`, used by
  `NavList`/`MobileDrawer`) had no `.catch()` on its Supabase query — a
  real network failure became an unhandled promise rejection and the
  component would wait forever instead of settling into an empty state.
  Fixed, with a one-time retry 30s later so it recovers automatically once
  Supabase comes back, without needing a hard refresh.
- **`/api/fragments/navigation`** and **`/api/fragments/footer`** (the
  two endpoints the nav/footer fetch client-side) now return a clean 200
  with empty data on failure instead of a 500 — the client already handled
  that gracefully, this just avoids it looking like a real error in
  monitoring.

### An important bug this caught (and fixed)

Running an actual `next build` — not just `tsc --noEmit` — surfaced a real
problem: Next.js signals its own build-time "can this route be static?"
probe by throwing a special error (`DYNAMIC_SERVER_USAGE`) when a route
touches `cookies()`. That's an internal control-flow signal Next needs to
receive, not a real failure — but the new try/catch blocks were catching
it right alongside genuine Supabase errors and misreporting it as "Supabase
is down, falling back to snapshot" for essentially every page (458 log
lines on the first build). Fixed with an `isNextControlFlowError()` guard
applied to every catch block (including one pre-existing gap in
`fragment-cache.ts` itself) that rethrows Next's own control-flow errors
unchanged. Re-running the build afterward showed exactly one fallback
log line — the one genuine case (Supabase unreachable from this sandbox)
— down from 458.

## Running it yourself

```bash
npm run generate:fallback   # refresh the snapshot manually, any time
npm run build                # also refreshes it automatically first
```

The script never fails the build: if Supabase can't be reached when it
runs, it logs a warning and leaves the existing snapshot file untouched.
No new environment variables are needed — it reuses
`NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`, the same
public, RLS-gated credentials the site itself already uses.

**Recommendation:** the snapshot only refreshes on deploy. If you publish
new games/categories/pages between deploys and then Supabase goes down
before the next one, visitors will see the catalog as of the last deploy,
not the last edit. If that gap matters to you, add a scheduled job (Vercel
Cron, GitHub Actions, etc.) that runs `npm run generate:fallback` every
hour or so and commits the result — I didn't wire this up since it needs a
decision about where that job runs and how it commits back to the repo.

## What this doesn't cover

**Supabase Storage.** If a game's thumbnail or a page's OG image is
hosted in Supabase Storage and *that* specific service goes down (as
opposed to the database), the JSON snapshot still has the correct URL, the
page still renders, but the `<img>` itself will fail to load until Storage
recovers. Fixing that would mean mirroring images to a separate host or
CDN — a meaningfully bigger project, not something to bolt on silently
here.

**True Next.js ISR / static HTML on a CDN.** As noted above, this is a
different mechanism from what was built — the pages here still render
per-request, they just don't fail when Supabase does. If you want actual
pre-rendered HTML served straight from the edge (a genuinely different,
faster failure mode — Supabase never even gets a chance to fail, because
nothing calls it on that request), that requires splitting the
personalized parts of pages (login state, continue-playing, country-based
ordering) away from a static shell, which is a real architectural change,
not a config flag. Happy to scope that separately if it's worth it to you.
